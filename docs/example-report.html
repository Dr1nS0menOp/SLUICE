Sluice report

Where you can send less to your SIEM without changing a detection, largest saving first, and the proof.

What this report means

A SIEM charges for every byte it receives, but its detection rules use only part of each event. Sluice compared the rules this SIEM runs with a sample of its data, and lists what no rule uses: mostly text that repeats fields the event already has, empty fields, values that follow from the kind of event (implied, explained below), and frequent events no rule can match, which are counted instead of sent one by one. This is not advice to collect less security data or to throw logs away. The savings assume a full copy of every event is kept in a cheaper archive; the configurations Sluice writes for Vector and Microsoft Sentinel keep one. On this sample, every alert was raised exactly as before. Nothing changes until your team reviews the proposed configuration and deploys it.

What “implied” means

A value is implied when the rest of the event already says what it is. That happens in two ways.

  • The kind of event fixes it. Every Windows event 4624 (a successful logon) comes from Channel Security, and Sentinel's Activity column holds the same text on each of them: 4624 - An account was successfully logged on. Such a text carries no data of the event itself: it is the event ID's description, which Microsoft's event reference on the internet gives for every ID (for 4624: 4624(S) An account was successfully logged on), so it can always be looked up again.
  • Another field fixes it. In the same event 4624, RestrictedAdminMode is - on every logon whose LogonType is not 10 (remote desktop), as the same reference says: once the SIEM has LogonType, it knows RestrictedAdminMode.

What Sluice does with it. It leaves the field out only on an event that holds exactly that value. An event with any other value in the field is sent with the field as it is. plan.json lists every implied value and when it applies, under remove_implied, so any tool can put the field back exactly. In Microsoft Sentinel, query <Table>Full instead of <Table>: Sluice writes that function, and it fills the fields back in. In Elasticsearch, the runtime fields Sluice writes do the same in searches and data views. The archive keeps every event whole.

How Sluice finds them. It learns them from this sample, and only on kinds of event frequent enough to be reduced at all: a rare kind of event is always sent whole. A value the kind of event fixes must be the same on every event of that kind in the sample. A field that fixes another must behave as a category: 2 to 32 distinct values, no value in the second half of the sample that the first half lacked, and a name that is not an identifier's (ending in Id or Guid, such as a logon ID). Each of its values needs at least 20 events before Sluice learns what it fixes. A field named as an identifier is itself fixed only by the kind of event, never by another field: a thread or a process one machine kept through the sample changes at its next restart. A field a detection rule reads is never left out of an event that rule could match.

When the data changes. If an event later holds another value, that event simply carries the field: the saving gets smaller, and nothing is lost or wrong.

The largest in this sample: TargetUserSid on windows-security events of the kind EventID=4624 [56 fields]. Why: fixed per value of TargetUserName: the sample has 6 pairs, such as TargetUserName = "alice" with TargetUserSid = "S-1-5-21-3623811015-3361044348-30300820-1100"; left out only when an event matches its pair, and put back from that pair. Leaving it out of 6,000 events saved 378 KB.

Together they save 1.5 MB. A value that is the same everywhere may belong to the machine the sample came from, such as its name or its domain, rather than to the kind of event. If so, events from other machines simply carry the field: the saving there is smaller, and no data is lost. A sample from several machines tells the two apart.
